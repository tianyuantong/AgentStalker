# AgentStalker 优化方案：证据判定与整改复测

日期：2026-09-20。方案状态：设计提案，尚未实施；本轮只读审阅代码，未运行项目测试或真实攻击实验。

审阅仓库：<https://github.com/tianyuantong/AgentStalker>。固定基线：`7d5748e71163eefa473f0a23f460d6f8aa2556ae`。

用户约束：接受证据充分性判定与整改复测；跳过模拟银行业务场景；功能提升应有实际价值，同时控制复杂度。

**推荐定位：在已有 Agent 安全审计框架上，补齐可解释的证据判定、可离线复核的证据包和可比较的整改回归。** 保留上游归属，独立贡献集中在这条链路。

## 1. 完成后应能演示什么

1. 相同日志输入，得到确定性的风险结论、支持证据和缺失证据说明。
2. 监控失效、请求失败、测试未执行，不再显示为安全。
3. 工具重名、关键词、模型拒绝等单一信号，不直接代替实际利用结果。
4. 一条漏洞用例，在已知易受攻击版本和修复版本上分别运行，正常功能同步验证。
5. 输出逐用例对比：本次未复现、仍可利用、新增回归、证据不足、不可比较。
6. 每个结论能找到原始记录、运行配置、目标与审计器版本；能区分重新分析旧证据与重新执行测试。

这些能力对应 JD 的技术验证、事件分析、漏洞治理、复盘整改。它们不构成生产级银行安全体系、合规认证或通用形式化证明。

## 3. 数据设计：三个问题分开记录

**执行是否完成、证据是否足够、有没有造成影响，分别判断。** 一个请求可能已经泄露数据，随后才超时；不能用执行失败覆盖已经确认的影响。

### 3.1 最小新增结构

复用现有 Evidence 和 ExecutionResult，在新字段或有版本的 metadata 中加入：

| 结构 | 最小字段 | 用途 |
|---|---|---|
| 运行上下文 | `run_id, case_id, attempt_id, session_id` | 唯一标识本次用例和重复次数 |
| 执行状态 | `completed / error / timeout / not_run`、失败阶段与原因 | 区分正常结果、请求失败和未执行 |
| 收集状态 | 每个必需来源的 `ok / error / not_enabled`、检查方法、完成窗口 | 区分确实没事件与取不到事件 |
| 断言结果 | `id, kind, status, evidence_refs, reason` | `kind=impact/normal`；`status=pass/fail/unknown` |
| 判定说明 | `reason_code, matched_rules, missing_evidence` | 给出机器可查和人工可读的依据 |

断言 pass 表示该命题成立，不等于攻击成功。例如 impact 断言 pass 可能证明外泄；normal 断言 pass 表示正常任务完成，两者不能混用。

用例中声明 `required_sources` 与适用范围，而不是强制全部八层监控同时在线。一个文件读取用例可以只需要工具响应和可信的测试文件；未启用 eBPF 不应自动否定该用例。

`ok` 不能只代表容器活着或 HTTP 返回 200，至少要证明对应采集接口可用、此次执行范围可辨认、结果读取完成。异步任务需要完成信号或预先定义的观察窗口；仅等待固定两秒不是通用的完成证明。

### 3.2 最终判定规则

保留现有 Verdict 枚举，收紧含义，避免大面积改调用方。

| 条件 | 最终结论 |
|---|---|
| 与当前执行关联的独立影响断言成立，且违反用例预先声明的权限/行为边界 | `EXPLOITED`；即使稍后超时仍保留，并同时显示执行异常 |
| 测试正常完成；必要观测完整；适用的影响检查明确为假 | `NOT_EXPLOITABLE`；界面写“本用例、本次运行未复现” |
| 存在具体风险信号，但缺少实际影响确认；本次测试本身有效 | `LIKELY_EXPLOITABLE`；展示为“风险线索，尚未确认利用” |
| 未执行、执行失败、必须的观测失效、未知断言、结果矛盾且无法消解 | `INCONCLUSIVE`；已有风险信号仍附在报告中 |
| 独立标注或人工复核已确认某项告警错误 | 可使用 `FALSE_POSITIVE`；不因本次未复现自动标为误报 |

首先检查可靠的正面影响证据，再判断是否具备给出负面结论的条件。拒绝文本不能覆盖实际副作用；缺日志不能给出负面结论。

现有 R001–R006、R009–R011 可作为风险线索来源。R009 的工具名冲突本身不再确认利用；R007 的拒绝和 R008 的空事件不再独立证明安全。规则异常必须留下错误信息，不能静默吞掉后继续给出安全结论。

LLM judge 仍可生成解释、建议下一步检查，但不能把证据不足升级为“确认利用”或“已安全”。原 confidence 数字保留兼容并注明是启发式分数，本轮不研究概率校准。

### 3.3 兼容策略

- 引入 `schema_version=2`，统一核心格式；旧格式通过入口适配器读取，原始文件保留。
- 缺少执行/收集元数据的旧证据默认 unknown，不凭空补成 completed/ok；不足以重新确认的结果保留历史结论但另列复核结论。
- 旧 runner 的 `vulnerable/safe/inconclusive/error` 只做输出映射，不保留独立决策逻辑。未确认风险绝不能映射 safe。
- 原有 `success` 继续表示传输或执行成功，不再兼任是否利用成功。
- 修正与新语义冲突的旧测试；不为了保持原断言而保留错误行为。
- JSON Schema 与实际序列化输出同步更新；加载时验证必要字段和版本。使用标准库 dataclass/Enum 与明确字段检查即可，不开发通用 schema 框架。

## 4. 证据关联与独立结果检查

### 4.1 轻量关联

由测试运行器生成上下文，传给 HTTP/MCP 调用包装层和采集器。HTTP 多轮使用同一个 session，并适配被测端实际使用的 session/conversation 参数；不能假定一个 trace header 自动维持会话。

能得到请求 ID 或工具调用 ID 时使用精确匹配；无法插桩的目标，首版采用每用例独立临时目录、独立进程/会话与串行执行。记录这是隔离范围关联，不能冒称全链路 tracing。只有时间相近，不足以确认因果关系。

只登记当前运行实际产生的文件，不能把整个 output 目录列为单条证据。记录原始位置、事件 ID、采集来源与内容摘要；证据字节的 SHA256 用于发现变化，不宣称抗恶意篡改或司法取证能力。

### 4.2 固定的断言函数

新增少量明确的 Python 检查函数，按名字注册。首版只实现演示需要的两类：

1. `protected_marker_returned`：预先在不允许访问的临时文件植入随机标记；检查本次工具响应是否返回它。标记不能写进攻击提示或正常响应中，否则可能只是回显。
2. `credential_received`：受控接收端记录本次请求，检查是否收到该次合成凭据；必须关联本次执行和未授权目标。

正常请求用精确响应/内容检查。通用关键词匹配继续用于筛选风险，不作为上述影响检查的替代。

未来可以加文件内容变化或真实工具分发结果检查，但不在首版同时实现。未知断言名、执行异常和输入格式错误均返回 unknown；不执行任意字符串表达式，不新造 DSL。

## 5. 整改复测与离线复核

### 5.1 两种操作必须分开

- `rejudge`：读取封存的原始证据，用新研判规则重新计算结论。用于验证审计器修改，不能证明被测系统已修复。
- `rerun + compare`：对易受攻击版本和修复版本分别执行同一套用例，再比较。用于验证目标整改。

现有 ConversationReplayExecutor 只负责按剧本重发对话，不承担以上两种比较功能。复用其会话执行能力，同时修复空断言与状态传播。

现有 correlation CLI 已能加载证据后再次 judge。`rejudge` 应当补齐并包装这个能力，主要新增正确的输出位置、版本记录、原始证据保护与输入校验，不另写研判器。

### 5.2 运行清单

每次保存一个 manifest，包括：

- 审计器 commit、规则版本/哈希；存在未提交变更时记录 diff 指纹。
- 被测目标 commit 或 fixture 内容哈希、权限配置和修复说明。
- suite/case 模板、断言实现、必要输入数据、初始状态及执行预算的指纹。
- Python/关键依赖版本、适用的平台/隔离配置。
- 使用真实模型时记录模型名与可得版本、采样参数、重复次数；未知版本明确标记，不假设 seed 能保证远端服务完全确定。
- 事件、响应、收集状态、断言结果和结论的路径与 SHA256。

不记录真实密钥。演示只用合成标记和合成凭据。

每次结果保存为 `runs/<run_id>/<case_id>/<attempt_id>/`。配置、证据与报告分开保存；离线复核输出写新文件，不覆盖原始结果。

### 5.3 可比较条件

整改对比必须使用同一审计器、用例模板、断言、权限前提、模型设置和执行预算。允许被测目标/策略的已声明修复变化。若同时修改检测器与被测目标，先把双方原始证据放到同一研判器复核，仍不得掩盖采集器变化。

run_id、临时目录和随机标记可以不同；比较的是它们的生成规则与含义，不能要求整个动态环境字节相同。目标行为配置中任何额外差异必须显示，不能用笼统的“忽略所有配置差异”放行。

模型、用例、断言或非预期权限变更时标为 `NOT_COMPARABLE`，不给改善百分比。增加新用例可以单列，不混入旧集合的改善率。

### 5.4 对比结果

| 前后变化 | 报告结论 |
|---|---|
| 前版本确认利用，后版本有效执行未复现，配对正常功能通过 | 本用例整改复测通过 |
| 后版本仍确认利用 | 仍可利用 |
| 前版本有效未复现，后版本确认利用 | 新增安全回归 |
| 正常请求前可用后失败 | 功能回归；不能用“禁用全部工具”算成功整改 |
| 后版本缺日志、失败或断言 unknown | 证据不足；不得算作修复 |
| 可比性检查不通过 | 不可比较，列出差异 |

没有易受攻击版本的正向结果，只能证明本次未复现，不能计算修复成功。报告还应显示初始状态重置是否成功，防止上一轮残留导致误判。

## 6. 演示范围：复用两项现有工具

不用银行业务背景，也不新增完整业务系统。保留原始易受攻击 fixture，新增修复变体或极小配置分支，便于审阅对比。

现有 [MCP fixture](https://github.com/tianyuantong/AgentStalker/blob/7d5748e71163eefa473f0a23f460d6f8aa2556ae/testbeds/mcp_mini_server/server.py) 可运行工具；Python mini agent 则主要是静态分析 fixture，其 query_db 只回显 SQL，不能当作现成业务 Agent。

| 演示 | 影响确认 | 修复 | 正常对照 |
|---|---|---|---|
| 文件工具超出声明目录读取 | 工具响应包含目录外合成文件的唯一标记 | 规范化路径后检查允许根目录，验证符号链接边界 | 允许目录内文件仍可完整读取 |
| 代理工具向未授权目标携带凭据 | 受控接收端实际记录到合成 Authorization | 移除通用凭据转发；仅对明确目标使用作用域受限的服务凭据，目标范围明确 | 允许的公开目标仍返回正确响应，不能简单禁用工具 |

首版代理修复演示可以只使用无需鉴权的允许目标，不实现 OAuth 平台。原 fixture 从环境变量取凭据，不能据此宣称已验证真实用户 OAuth token passthrough；测试结论限定为该配置下的错误转发。

文件目录检查仅在固定测试目录与受控环境验证，不宣称解决任意并发文件替换/TOCTOU。演示包含合法同前缀兄弟目录、`..` 和符号链接边界，但不扩展为全套文件沙箱。

MCP 直接调用证明工具边界和审计链；不能把这些结果写成真实大模型的提示注入成功率。真实模型端到端验证为单独一层，在基础链路完成后选择一个固定目标和少量用例，明确写出模型与运行限制。

## 7. 评测与验收

### 7.1 三层证据

| 层 | 起步规模 | 证明内容 |
|---|---|---|
| 判定逻辑 | 约 24 个固定、带独立预期的证据用例 | 判定规则正确、错误状态不误报安全、两入口一致 |
| 真实局部集成 | 两个 MCP 工具；约 12 个模板在前后版本各运行一次 | 文件/HTTP 副作用、整改对比、正常功能和故障状态确实被采集 |
| 真实模型端到端 | 完成前两层后，选一个目标、3–5 条用例并重复运行 | 模型、工具与取证链是否能连通；不推算全行业检测率 |

这是建议规模，不是已有成绩。前两层是首版必须完成；第三层若因环境/API 条件未执行，必须在项目展示中明确留空，不能以 mock 结果替代。

固定证据至少覆盖：正常空事件、采集失败、未执行、超时、拒绝后仍有副作用、重名未调用、跨 run 混合事件、未知断言、合法相似内容、延迟副作用、目标允许的敏感行为、规则抛错、旧格式缺字段、修复前正向对照缺失。

核心回归性质：

- 添加无关 run 的事件不能改变本次结论。
- 对同一原始证据重复分析结论一致；唯一时间戳等元数据不参与语义比较。
- 删除必要观测不能让结果变为安全。
- 超时后已有有效正向证据不能被降为未利用。
- 未知/损坏输入不能通过门禁。
- 两个入口对同一规范化证据给出相同结论。
- 对“修复只是停止服务”的候选版本，正常对照必须揭示功能回归。

期望标签由独立测试事实或人工审阅确定，不能复制旧规则输出作 ground truth；保留若干未用于调规则的边界用例。误报统计必须有明确正常标签，不能把所有未确认样本都当作误报。

### 7.2 指标口径

- 始终先报告计划用例总数、实际尝试数、执行失败数、证据不足数、可判定数。
- 攻击成功率仅在定义清楚的可判定攻击尝试中计算，显示分子/分母和有效覆盖率；超时但影响已确认的尝试仍计成功。不能靠删去失败记录改善数字。
- 已标注正常样本的错误利用确认数/正常样本数；风险线索告警单独统计。
- 已标注攻击样本的漏确认与 unknown 分开展示，避免全部返回 unknown 获得虚假的低误报成绩。
- 整改复测通过数/可比较且基线确实成功利用的配对数，同时列出排除项。
- 正常任务完成数/正常任务总数。
- 可复核证据包数/运行包总数；包含规范化结果、manifest 和必要原始记录。
- 若真实模型运行，逐用例列出每轮结果与成本，不只保留最好一次。少量自建样本不宣称统计泛化。

首版硬验收：预设关键负例全部按预期处理；两个演示有修复前后的真实局部副作用记录；配对正常功能通过；重复输出不覆盖；损坏证据或不可比输入不能生成“整改通过”。

### 7.3 CI

默认 CI 跑纯判定测试和轻量 MCP/本地接收端集成，不依赖外部 API key、Docker、eBPF。使用现有 pytest，新增依赖优先为零。

在独立临时目录中执行 fixture，向子进程传最小环境和合成凭据，不继承真实 AUTHORIZATION 或访问用户文件。HTTP 接收端仅用于测试并在完成后关闭；此约束服务于实验隔离，不宣称是敌对代码的强沙箱。

候选整改门禁：0 表示必要用例有效且通过；1 表示已确认安全/功能回归或仍未修复；2 表示执行错误、证据不足或不可比较。混合结果仍须在报告中完整展示。测试套件本身测试易受攻击 fixture 时，以匹配独立预期为成功，不能因为预期发现漏洞就把开发 CI 判失败。

## 8. 控制复杂度的实现范围

优先只增加三个生产代码文件：

| 新模块 | 职责 |
|---|---|
| `sandbox/contracts.py` | 运行上下文、收集状态、断言结果及字段验证；复用已有 Evidence，避免再造第三种结果模型 |
| `sandbox/assertions.py` | 少量明确的结果检查函数和名称注册表 |
| `sandbox/regression.py` | manifest、可比性检查、离线复核与结果对比；不负责另造执行引擎 |

修改现有 `correlation/__init__.py`、`test_runner.py`、`api_executor.py`、`replay.py`、必要 MCP 包装层与证据 schema。采集器按首版所需来源接入；未适配的旧来源必须明确 unknown，不一次性改完八层监控。

规则以 Python 实现为唯一可执行来源；`sandbox/data/verdict_rules.yaml` 保留为说明并同步修正，或从规则元数据生成摘要；不新增 YAML 表达式解释器。不要让文档规则和代码成为两个决策引擎。

报告继续使用 Markdown + JSON，只增加状态、证据引用、逐用例差异和指标。暂不新增 Web UI、数据库、消息队列、服务端平台、统一安全网关或新 AST 引擎。OPA 的通用整改、Rust 调用图优化、语义概率校准、更多框架适配均列为后续候选，不进入本轮依赖链。

拟议命令形态（尚未实现，参数以实现时收敛为准）：

```text
python -m sandbox.test_runner --config suite.json --profile vulnerable.json --output runs/before
python -m sandbox.test_runner --config suite.json --profile fixed.json --output runs/after
python -m sandbox.regression compare runs/before runs/after --output reports/compare
python -m sandbox.regression rejudge runs/before --output reports/rejudged
```

新 profile 只描述首版必要的 HTTP/MCP 执行参数与 fixture 初始状态，不发展成通用部署配置系统。打包时检查新增模块及原有子包可从安装产物导入；现 pyproject 仅显式列出顶层包，不能只用源码目录 PYTHONPATH 成功作为安装验收。

## 9. 实施顺序与预算

以下是工作量估计，不是交付承诺；开始实施后先跑基线，按真实环境修正。

| 阶段 | 内容 | 粗估投入 | 结束条件 |
|---|---|---:|---|
| 0 基线冻结 | 保存 commit、环境、已有测试通过/失败/跳过清单，建立少量失败复现用例 | 3–5 小时 | 现状可重复，历史宣传结果与当前结果分开 |
| 1 判定收敛 | 统一两个入口、执行/取证状态、LLM 权限边界、旧格式兼容 | 10–14 小时 | 空日志/错误/重名/拒绝等关键负例通过 |
| 2 证据与执行 | 唯一运行目录、会话修复、必要前置条件、两种独立结果检查 | 10–16 小时 | 两个工具在易受攻击版本产生真实证据，故障被正确记录 |
| 3 整改对比 | 修复变体、正常对照、manifest、可比性、compare/rejudge | 10–14 小时 | 前后配对报告可解释且能复核 |
| 4 交付 | 边界测试、CI、安装检查、README、两份案例和演示脚本 | 6–10 小时 | 新环境可按说明运行，成果边界清楚 |

核心约 39–59 小时，可按约 2 周有效开发时间安排。真实模型/外部目标验证另预留 4–8 小时起步；若环境搭建变成主要耗时，先保留完整的工具层结果和明确边界，不为了跑通模型而重构整套沙箱。

按上述阶段组织可独立审阅的提交。每一步完成后看失败用例、diff 和证据，再进入下一步；此方案本身不包含执行、推送或创建 PR。

范围停止条件：两个示例、三类结果状态、两入口统一、前后比较和正常对照完成即可交付首版。新增抽象只有在出现第二个实际复用点时再考虑。

## 10. 展示与面试材料

交付应包括：一份设计与取舍说明、固定测试集及标签说明、CI 记录、两份整改前后案例、样例证据包、简短运行步骤，以及上游能力/本人新增能力对照表。

实现后可据实际情况使用的描述模板：

> 基于 AgentStalker 改进 Agent 安全审计的证据判定与整改回归，统一双判定入口，区分执行失败、证据不足和确认利用；实现按运行隔离的证据归档与离线复核，并在文件访问和凭据转发两类 MCP 工具场景中完成修复前后及正常功能对照验证。

只有完成真实模型集成，才增加“真实 Agent 端到端验证”的描述。数字填入实际测试报告，不沿用上游的成功率和测试数量作为个人成绩。

适合准备的面试问题：为什么空日志不能证明安全；为什么执行失败仍可能确认利用；如何证明事件属于同一次攻击；为什么工具重名只是线索；如何避免通过禁用功能得到虚假整改结果；离线重判和实际复测有什么区别；固定测试集的结果能推广到什么范围。
